# 后续执行计划

## 1. 计划目标

本文档基于当前已有的项目总览、业务域模型、后端设计、前端设计、API 契约、数据库设计、实施计划、下一步开发计划和后端工程骨架设计，进一步沉淀后续可执行计划。

当前项目已经完成方案与骨架设计，下一步不再继续扩写概念文档，而应进入工程初始化与 MVP 主链路实现。

后续计划的核心目标是：

**在首个开发周期内完成可本地启动、可接口联调、可演示购买与兑换闭环的 MVP。**

```text

├─ backend
├─ apps
│  ├─ web

```

第一版支付使用 Mock 支付回调，第一版库存导入使用 CSV 或文本批量导入，第一版交付结果按账号密码模式处理。

- 完成商品下单
- 完成 Mock 支付创建与支付成功回调
- 支付成功后生成或绑定 CDKey

建议周期：

- 3 到 4 天

输出物：

- `POST /api/orders`
- `GET /api/user/orders`
- `GET /api/user/orders/{orderNo}`
- `POST /api/payments/create`
- `GET /api/payments/status/{orderNo}`

## 5. 推荐开发顺序

建议严格按以下顺序推进：

1. 工程骨架
2. 数据库与后端公共层
3. 认证与商品接口
4. 订单与支付接口
5. CDKey 发放与查询
6. 库存导入与兑换接口
7. 用户端页面联调
8. 管理后台页面联调
9. 日志、风控、部署与演示数据

不建议先做复杂报表、真实支付渠道、优惠券、对账、客服工单、分销等扩展能力。

## 6. 关键决策默认值

若没有额外产品要求，MVP 阶段按以下默认值推进：

- 目录结构：Monorepo
- 支付方式：Mock 支付
- 库存导入：CSV 或多行文本
- 交付类型：账号密码
- 用户注册：用户名、密码、邮箱，不接短信验证码
- 管理员账号：初始化 SQL 或启动脚本内置一个开发账号
- CDKey 生成：后端生成全局唯一编码
- 权限模型：先区分用户端与管理员端，后台细粒度权限后置
- 部署方式：先本地开发，后补 Docker Compose

## 7. 风险控制重点

## 7.1 状态一致性

重点关注：

- 订单状态
- 支付状态
- 交付状态
- CDKey 状态
- 库存状态

要求：

- 所有状态值必须定义枚举
- 状态流转必须由业务方法封装
- 禁止散落字符串更新状态

## 7.2 幂等与并发

重点关注：

- 支付回调重复通知
- 用户重复点击兑换
- 同一 CDKey 重复提交
- 多人同时兑换同一商品库存

要求：

- 支付回调以支付单号或第三方流水号做幂等
- 兑换入口使用 Redis 锁
- 库存分配使用数据库行锁或状态条件更新
- CDKey 编码和订单号依赖唯一索引兜底

## 7.3 敏感信息

重点关注：

- 库存账号密码
- 交付结果
- 支付回调原文
- 管理员操作日志

要求：

- 库存密码密文存储
- 管理后台默认脱敏
- 日志禁止输出明文密码
- 导出能力延后实现

## 9. 最小演示脚本

演示前准备：

- 创建一个上架商品
- 导入至少 3 条库存账号
- 创建一个普通用户
- 创建一个管理员用户

演示路径：

1. 用户登录
2. 进入商品详情
3. 创建订单
4. 发起 Mock 支付
5. 触发支付成功回调
6. 用户进入我的 CDKey
7. 用户复制 CDKey 并兑换
8. 系统返回交付结果
9. 管理员登录后台
10. 管理员查看订单、库存和兑换记录

演示通过标准：

- 全流程无需手动改数据库
- 页面状态与接口状态一致
- 每个关键动作都有明确成功或失败反馈

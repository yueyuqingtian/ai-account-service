# 下一步开发计划

## 1. 文档目标

本文档用于承接当前方案阶段的输出，将现有的业务、架构、接口、数据库文档转化为可执行的开发计划。

当前项目状态：

- 仓库已完成方案文档初始化
- 仓库尚未创建前后端代码骨架
- 业务主链路尚未进入实现阶段
- 支付、库存导入、风控仍停留在设计层

本文档聚焦的目标是：在最短路径内完成一个可联调、可演示、可扩展的 MVP 版本。

## 2. 当前开发基线

基于现有文档，当前开发必须遵循以下基线：

- 后端使用 `Java 21 + Spring Boot 3 + Spring Security + MyBatis-Plus + Redis + PostgreSQL`
- 用户端使用 `Vue 3 + Vite + TypeScript + Pinia + Vue Router`
- 管理后台使用 `Vue 3 + Vite + TypeScript + Pinia + Element Plus`
- 后端先按单体分层设计实现，不做微服务拆分
- 核心主链路优先：`商品 -> 订单 -> 支付 -> CDKey -> 兑换`

## 3. 下一步总目标

下一阶段的核心目标只有一个：

**完成首个可联调版本，并打通商品浏览、下单、支付确认、CDKey 发放、CDKey 兑换、后台库存导入这 6 个关键环节。**

## 4. 执行原则

- 先契约，后编码
- 先主链路，后边缘能力
- 先可跑通，后做优化
- 先保状态一致性，后做运营能力
- 任何影响订单、支付、兑换状态流转的逻辑，必须先定义清楚状态机与异常回滚策略

## 5. 阶段拆解

## 阶段 A：项目初始化与骨架搭建

### 目标

建立前后端基础工程，使团队可以并行开发。

### 任务清单

- 初始化后端工程
- 初始化用户端工程
- 初始化管理后台工程
- 初始化数据库连接、Redis 连接、配置分环境方案
- 初始化统一响应结构、异常处理、日志规范
- 初始化前端请求层、路由层、状态管理层

### 输出物

- `backend/` 后端工程目录
- `apps/web/` 用户端工程目录
- `apps/admin/` 管理后台工程目录
- 环境配置模板
- 基础启动说明

### 验收标准

- 三个应用均可本地启动
- 后端具备健康检查接口
- 前端具备基础路由与登录态存储能力
- 所有工程具备最小可运行结构

## 阶段 B：数据库与基础实体落地

### 目标

将设计文档转成可执行的数据库结构与后端实体。

### 任务清单

- 编写建表 SQL
- 建立用户、商品、订单、支付、CDKey、库存、兑换、管理员、日志表
- 建立主键、唯一索引、组合索引
- 建立后端 Entity、Mapper、DTO、VO 基础结构
- 定义枚举：订单状态、支付状态、CDKey 状态、库存状态

### 输出物

- `sql/init_schema.sql`
- 基础实体类
- 基础 Mapper
- 枚举类与常量类

### 验收标准

- 本地数据库可成功执行建表脚本
- 核心表主键、索引、唯一约束正确
- 后端基础实体和表结构一一对应
- 枚举值与文档定义一致

## 阶段 C：后端主链路实现

### 目标

完成核心业务链路的后端闭环。

### 任务清单

- 实现用户注册登录
- 实现商品列表与商品详情接口
- 实现创建订单接口
- 实现创建支付单接口
- 实现支付成功回调接口
- 实现支付成功后发放 CDKey 的流程
- 实现用户查询订单与 CDKey 列表接口
- 实现 CDKey 兑换接口
- 实现库存分配逻辑与兑换日志记录

### 输出物

- 用户端 API 第一版
- 后台端库存导入 API 第一版
- OpenAPI 文档

### 验收标准

- 已支付订单能生成对应 CDKey
- 同一支付回调重复通知不会重复发卡
- 同一 CDKey 不会被重复兑换

## 6. 推荐开发顺序

建议按以下顺序执行，不建议打乱：

1. 先初始化三个工程骨架
2. 再落数据库 SQL 与后端实体
3. 再写后端主链路接口
4. 再写用户端页面并联调
5. 再写管理后台 MVP
6. 最后补日志、风控、部署说明

## 9. 风险点与应对

## 风险 1：支付与订单状态不一致

应对：

- 支付回调必须幂等
- 订单状态更新必须加事务
- 先记录回调原文再更新业务状态

## 风险 2：CDKey 重复发放或重复兑换

应对：

- CDKey 编码唯一索引
- 兑换接口增加 Redis 锁
- 数据库层做状态条件更新

## 风险 3：库存资源被重复分配

应对：

- 库存按状态锁定
- 分配过程使用事务和行锁
- 分配成功后立即写入兑换记录

## 风险 4：前端页面先做完但后端契约变化

应对：

- 先冻结 DTO/VO
- Mock 数据结构必须与 API 契约一致
- 禁止前端自行发明字段

## 11. 进入编码前的准入条件

开始正式写代码前，需要先确认：

- 是否采用 Monorepo 目录结构
- 支付渠道第一版是否先用 Mock 回调代替真实支付
- 库存导入格式是否使用 CSV
- 交付结果是否固定为账号密码模式
- 用户体系是否需要短信/邮箱验证码

如果这些项没有确认，建议先按 MVP 默认值推进，但要在文档中固化默认约束。

## 12. 开发完成定义

下一阶段完成的定义不是“写完一些代码”，而是满足以下条件：

- 三个应用骨架已建立
- 数据库脚本可执行
- 主链路后端接口已联通
- 用户端可以完成一次完整购买与兑换演示
- 管理后台可以完成库存导入与记录查看
- 关键状态流转有日志可追踪
